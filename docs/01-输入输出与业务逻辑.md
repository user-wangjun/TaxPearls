## 二、输入（Input）

### 2.1 输入类型与来源

| 输入类型 | 来源 | 处理方式 | 优先级 |
| --- | --- | --- | --- |
| **科目余额表** | 财务软件直接导出 | 主入口。结构化、信息密度最高 | P0 |
| **纳税申报表** | 电子税务局 | 结构化解析 | P0 |
| **三大报表** | 财务软件 | 结构化解析 | P0 |
| **发票明细** | 电子税务局批量下载 | 走电子数据（XML/Excel），**不 OCR** | P1 |
| 银行流水 | 网银导出 | 结构化解析 | P1 |
| 社保 / 公积金记录 | 社保平台 | 交叉校验用 | P2 |
| 合同 | 用户上传 | 四流一致校验，人工勾选辅助 | P2 |
| 纸质票据 / 照片 | 扫描件 | **OCR 兜底路径，非主路径** | P2 |

### 2.2 Web 材料接收（2026-09-22 更新）

支持同时选择 Excel / XML / PDF，以及 ZIP 内的多份材料。用户明确选择“同一企业同一期间合并”或“每个文件分别审计”；不按文件名猜测客户归属。已识别的企业、期间或同名指标存在冲突时拒绝合并。多份发票 XML / Excel 按票号去重；多份来源银行流水按银行唯一编号/交易流水号去重，无唯一编号的旧统一模板不得跨文件合并。

文字 PDF 先提取原文和明确的单值候选指标，再由用户核对金额列、单位、期间与口径后提交。现已增加可配置的 AI 材料提取层：视觉模型可接收本地渲染的 PDF 页面图片，纯文本模式只接收文字；输出标准指标、原值、单位、页码与原文引用，由后端校验并换算，进入人工确认。未配置或失败时明确提示并支持补录，真实视觉识别质量待填入密钥验证。不能识别的项目不补零；可用指标进入原规则引擎，材料不足的规则保持“未执行”。每项证据携带文件名、内容指纹、表格位置或 PDF 页码与人工核对说明。

Excel 账表仍按标准工作表/列头读取；发票和银行来源 Excel 另按下节列出的表头别名映射。允许把独立报表、银行来源流水和调节底稿分文件上传。每次最多 20 份，单文件 / ZIP ≤ 10MB、解压后合计 ≤ 50MB，PDF ≤ 50 页；原始文件不持久化，核对任务有效期 10 分钟。

### 2.3 发票电子数据适配（2026-09-22 实现）

支持两个确定的结构化来源：

1. **财政部数电发票 XBRL XML**：按财政部《[电子凭证会计数据标准——全面数字化的电子发票（推广应用版）](https://kjs.mof.gov.cn/zt/kuaijixinxihuajianshe/dzpzkjsjbzshsd/sjbz/202505/t20250519_3964020.htm)》的 `InvoiceNumber`、`RequestTime`、`TotalAmWithoutTax`、`TotalTaxAm`、`TotalTax-includedAmount`、红字标志、会计主体、用途确认和进项转出元素读取；忽略命名空间前缀但要求财政部 XBRL 命名空间。[国家税务总局的数电票说明](https://www.chinatax.gov.cn/chinatax/n810356/n3010387/c5236173/content.html)也明确保留 XML 数据电文格式，因此 XML 走电子数据路径而不是 OCR。
2. **发票来源 Excel**：保留统一 `发票明细` 六列模板；来源表可使用“数电票号码/发票号码、开票时间/开票日期、不含税金额/合计金额、合计税额/税额、价税合计、发票状态、销购方税号、用途确认、确认所属期、进项转出”等列名。发票方向依次按显式销项/采购、工作表名、企业与销购方税号判定；无法唯一判定则拒绝，不猜测。

统一口径如下：

- 正常票正计，红字票按金额绝对值冲减，作废票保留张数但不计金额；同一文件或跨文件票号重复一律拒绝。
- 不含税金额与税额分开汇总；提供价税合计时，必须满足 `价税合计 = 不含税金额 + 税额`，允许 0.01 元舍入差。
- `发票.采购税额净额`表示采购有效票税额净额；`凭证.本期确认抵扣税额`只纳入明确确认“抵扣税款”、确认期落在审计期内的采购票，并扣减明确的进项转出。未确认用途不等于零，也不自动视为可抵扣。
- 开票日期必须落在核对所属期。XML 禁止 DTD / 实体声明并限制元素数量与嵌套深度；解析不等于验真或数字签名验证，界面会持续提示该边界。

### 2.4 银行来源适配与收入调节（2026-09-22 实现）

确定来源基线采用建设银行《[企业网上银行客户操作指南](https://ccb.com/su/share/fhgg/20150720_1437377810/20150720153909659777.pdf)》公开展示的“唯一编号、交易日期、借方发生额、贷方发生额、余额、对方户名、对方账号、摘要”等字段；同时接受“交易流水号/交易序号、收入/支出金额”或“交易金额 + 收支方向”等同义列。借方视为支出、贷方视为收入；当前自动口径只接受人民币。该映射是已验收的字段契约，不宣称兼容未取得样本的所有银行和版本。

数据分为三层，任何一层都不能被下一层悄悄替代：

1. **原始流水层**：保留流水号、交易日期、收入/支出、摘要、来源文件指纹和工作表行号，产出 `银行.收入流水合计`、`银行.支出流水合计`。原始入账只是资金事实，不是营业收入。
2. **逐笔分类层**：`银行调节`按流水号关联每笔收入，分类为经营回款、借款、内部转账、资本金、往来款、预收款、保证金、退款或其他非经营；明确填写权责所属期、本期不含税收入、底稿编号、复核状态和说明。非经营/往来分类的本期不含税收入必须显式为 0。
3. **权责调节层**：没有对应银行入账的现金收入、应收收入、跨期补计/扣减、退款折让等，以独立调节行记录金额和加减方向。系统生成 `银行.经营回款已复核不含税额`、`银行.权责口径调节额`，两者相加成为 `银行.调节后不含税收入`，供 R-015 使用。

`银行调节`严格表头为：`调节编号 / 流水号 / 分类 / 权责所属期 / 本期不含税收入 / 调节金额 / 调节方向 / 底稿编号 / 复核状态 / 说明`。只有全部收入流水具有唯一编号、恰好分类一次、全部“已复核”，且底稿与期间完整，才生成调节后收入。重复流水号、外币、跨核对期原始流水、未分类/未复核、错误引用、非经营款计入收入、独立调节缺方向或最终收入为负均拒绝。账号仅在短期核对草稿中以掩码提示，完整账号和原始文件不持久化。

### 2.5 关键判断

- **主输入是「科目余额表 + 申报表 + 发票汇总」，不是「一叠发票照片」。** 前者已聚合、带会计含义；后者原始、异构、需识别。
- **「标准化」是最脏也最核心的一步**：各财务软件科目编码、期间口径、辅助核算口径不一致，须统一到同一套内部口径，否则后续规则一条都跑不起来。这是隐藏的护城河。

## 三、输出（Output）

必须**分两层**，只给结论等于黑盒。

### 3.1 警示层（面向经营管理者）

- 风险等级：高 / 中 / 低
- 一句话结论，例：「本企业存在隐匿收入的重大涉税风险」

### 3.2 证据层（面向会计、教师）—— 产品价值所在

每条风险点必须可展开为一张**证据卡**：

```
风险类型：收入未足额申报
命中规则：R-001 账面收入 vs 增值税申报销售额偏离度 > 10%
触发明细：
  利润表 营业收入            1,280,000.00
  增值税申报表 销售额          860,000.00
  偏离度                          32.8%
法条依据：《中华人民共和国增值税暂行条例》第一条
建议动作：核查是否存在未开票收入未申报，或视同销售未确认收入
```

> **没有证据层，产品就是黑盒；有证据层，每句话都能被追问。** 这是答辩中最硬的资产。

### 3.3 实训场景的第三层输出

学生的答题结果 vs 标准答案的集合比对：

- 查出的风险点（得分）
- **漏检项**（扣分，附标准答案）
- **误报项**（扣分，说明为何不构成风险）
- 评分依据明细

评分标准本身的合理性，是教师认可度的关键。

## 四、业务逻辑

审计的本质是**比对**。所有风险来源可归为三类：

### 4.1 内部勾稽（账内自洽性）

无需外部数据，仅凭企业自身材料即可校验：

- 利润表收入 vs 增值税申报销售额
- 资产负债表未分配利润变动 vs 利润表净利润
- 进项税额 vs 存货 / 成本变动

### 4.2 外部交叉（账面 vs 外部真实数据）

金税四期的核心逻辑，最有说服力：

- 账面收入 vs 银行流水
- 个税申报人数 vs 社保参保人数
- 进项采购规模 vs 销项开票收入
- 报表人数 / 资产 vs 小微企业优惠认定条件

### 4.3 指标偏离（横向 / 纵向对标）

- 税负率 vs 同地区同行业均值
- 毛利率同比 / 环比异常波动
- 连续亏损却持续扩张

### 4.4 主干流程

```
取数 → 标准化 → 三类比对 → 命中规则 → 定级 → 生成证据卡 → 出清单/报告
```

## 五、规则库：YAML 声明式

### 5.1 两类规则，两条路径（不可混淆）

| 类别 | 执行方式 | 用途 | 占比 |
| --- | --- | --- | --- |
| **条件规则** | YAML 声明 + 求值引擎（字段间比对、阈值判定） | 绝大多数风险点 | ~90% |
| **图规则** | 图查询（节点与关系的模式匹配） | 关联方识别、关联交易网络 | ~10% |

> ⚠️ **不要把「YAML 条件规则」与「SPARQL / 图查询」混为一谈。**
> - 条件规则是 **if-then 求值**：「利润表收入 比 申报销售额 高 10% 以上」——与图无关。
> - 图查询是 **关系网络遍历**：「找出 A 的股东 → 这些股东控制的其他公司 → 它们之间的交易」。原来规划的「知识图谱」能力落在这一路，需求保留，但应作为独立的图规则引擎，不塞进 YAML 引擎。

### 5.2 条件规则结构示例

> 下例为早期结构草案，不能作为当前可执行格式。2026-09-21规则包已升级为2.0，
> 增加完整取数/适用范围/阈值元数据，并使用2026年生效的增值税法；
> 请以 `rules/` 和 [核对规则目录与使用说明](03-核对规则目录与使用说明.md) 为准。

```yaml
id: R-001
name: 收入未足额申报
tax_type: 增值税
severity: high
inputs: [利润表.营业收入, 增值税申报表.销售额]
logic:
  type: deviation          # 偏离度判定
  left: 利润表.营业收入
  right: 增值税申报表.销售额
  threshold: 0.10          # 偏离 > 10% 命中
evidence: [利润表.营业收入, 增值税申报表.销售额, computed.deviation_rate]
legal_basis: [《中华人民共和国增值税暂行条例》第一条]
suggestion: 核查是否存在未开票收入未申报，或视同销售未确认收入
```

**设计要点**：每条规则自带 `evidence` 与 `legal_basis`，使「可举证」成为规则的固有属性，而非事后拼装。会计 / 教师可参与编写规则，无需写代码。

### 5.3 审计与出题是逆运算

```
审计模式：真实账套 → 规则引擎 → 风险清单（带证据）
出题模式：目标规则 → 规则引擎（反向） → 带标注题库（带标准答案）
```

**规则库是唯一真相源。** 出题器读取规则的 `inputs` 与 `threshold`，反向构造能命中该规则的数据（例：把两个数拉开到 30%），即可自动生成题目。同一份规则定义，两种执行方向，无需另写题库系统。

## 六、数据安全基线（P0 必须落地）

财务数据 = 企业商业秘密 + 个人信息（法人、股东、员工身份证、银行账号）混合，涉及《数据安全法》《个人信息保护法》《网络安全法》。

| 层面 | 要求 |
| --- | --- |
| 传输 | 全站 TLS 1.2+，禁止明文 HTTP |
| 密码存储 | argon2 / bcrypt 加盐哈希，**严禁明文、MD5、SHA1** |
| 敏感字段 | 身份证号、银行账号、手机号**列级加密**存储 |
| 租户隔离 | 多租户行级权限，机构间数据互不可见 |
| 最小权限 | 会计仅可见自己负责的客户；导出需二次确认 |
| 审计日志 | 谁、何时、查看/导出了哪条数据，全量留痕 |
| 数据不落地 | 导入即解析，非必要不留存原始文件 |
| 备份 | 加密备份 + 明确的销毁策略 |
| 环境隔离 | 演示 / 培训环境与生产环境物理隔离 |

### 🚨 红线

> **沙箱中的训练数据必须是仿真数据，严禁使用真实企业账套作为教具。**

一旦使用真实客户数据做教学案例，性质即变为数据泄露事件。反过来说——**沙箱采用仿真数据，从源头消灭了最大的一块数据安全风险**，这是实训业务线在合规上天然优于真实审计业务线的关键理由，也是它作为主线的支撑之一。

## 七、MVP 定义与验收标准

### 7.1 P0 范围（做）

1. 导入一张标准模板的科目余额表（Excel）
2. 加载 1 条 YAML 规则
3. 引擎求值 → 命中
4. 输出 1 张证据卡：两个数值、偏离度、命中规则、法条依据、建议动作

### 7.2 P0 明确排除（不做）

UI 美化、多规则、报告导出、登录鉴权、多租户、OCR、RPA、图规则、LLM 解读层

### 7.3 验收标准

> **给一张 Excel，能在页面上看到「这条为什么有问题」的完整证据链。**

**顺序不可颠倒**：先把「可举证」这条路打通，再往上堆规则。若反过来先堆 50 条规则而证据链是空的，则 50 条全是不可解释的黑盒，价值为零。
