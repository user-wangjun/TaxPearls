## 1. 结论先行

1. **建议走「旁挂明细表」方案（方案 B），不改 `submissions` 表结构。**
   `submissions` 继续只保存「当前这一次正式提交」，新增三张表分别承载草稿、历史版本、学生进度状态。这样 15 处既有读写点**一行都不用改**，回滚只是删三张新表。
2. **必须先修一个真问题**：现有链路**没有实现「一人只能提交一次」**，且重交会**直接清空教师复核结果**。这不是「缺功能」，是数据丢失。
3. **真库当前是干净的**：`submissions` / `assignments` / `training_papers` 各 0 行。所以本次迁移不存在历史数据兼容负担 —— 但这也意味着**缺陷还没有被真实课堂数据放大过**，越早修越好。
4. 方案 B 落地前有 **4 个产品口径需要你拍板**（第 6 节），不然代码写出来一定返工。

## 2. 为什么现在必须动：实测到的缺陷

用临时库跑了一次探针（教师建班→发布单案例作业→学生连交三次→教师复核）：

```
student can_submit after submit: True      ← 交完还能交
1st submit: 200 | 2nd submit: 200          ← 覆盖式重交
teacher sees rows: 1                       ← 教师端只看到 1 行，看不出交了几次
after review adjusted_score: 88.0          ← 教师给了 88 分
3rd submit after review: 200               ← 复核后学生又交了一次
adjusted_score after resubmit: None        ← 88 分被抹成 NULL，复核意见一起没了
```

**根因在代码里是三处叠加：**

| 位置 | 现状 | 后果 |
| --- | --- | --- |
| `webapp/classroom.py:81` | `can_submit = published and not deadline_passed` | 只看发布和截止，**不看是否已交** |
| `webapp/app.py:1995` | 只校验 `can_submit` 与截止 | 重复提交直接放行 |
| `webapp/storage.py:1556-1560` | `ON CONFLICT ... DO UPDATE ... adjusted_score=NULL, feedback=NULL, reviewed_by=NULL` | 覆盖时**主动清空复核** |

设计文档（`高校端-教学端重设计方案-待确认.md` §5.1）要求「订正新增提交版本，保留原稿和原成绩」。现状是**没有任何版本，原稿和原成绩被就地覆盖**。B3 不做，这条永远是隐患；而做之前必须先定「重交到底允许几次、谁来开」。

## 3. 现有结构的硬约束

`webapp/schema.py:70-76`：

```sql
CREATE TABLE submissions (
  id TEXT PRIMARY KEY, assignment_id TEXT NOT NULL REFERENCES assignments(id),
  student_id TEXT NOT NULL REFERENCES users(id), answers_json TEXT NOT NULL,
  score REAL NOT NULL, details_json TEXT NOT NULL, submitted_at TEXT NOT NULL,
  adjusted_score REAL, feedback TEXT, reviewed_by TEXT REFERENCES users(id),
  UNIQUE(assignment_id, student_id)          -- ← 一人一题只能一行
);
```

四条硬约束，决定了方案选择：

| 约束 | 说明 | 对迁移的影响 |
| --- | --- | --- |
| `UNIQUE(assignment_id, student_id)` | 一人一题一行，靠 upsert 覆盖 | 要存多次提交，**必须绕开**（不能靠加列解决） |
| `ON CONFLICT(...) DO UPDATE` | `storage.py:1556` 的写法绑定这个唯一键 | 改唯一键就得同步改这条 SQL |
| `details_json` / `feedback` 是**加密列** | `sensitive_storage.py:32` 注册：身份键 `(assignment_id, student_id)`，AAD 绑定表名+列名+身份键 | **新表存同类数据必须先在 REGISTRY 注册**，否则解密失败 |
| SQLite 不支持 `ALTER TABLE ... DROP CONSTRAINT` | 改唯一键 = 重建表 | 只能「建新表→拷数据→删旧表→改名→重建索引」 |

另外两个有利事实：

- **没有任何外键指向 `submissions(id)`**（全仓 grep 为 0），也没有触发器和视图 —— 重建表不会被级联引用拖住。
- 仓库里**已有 attempt 表的先例**：`training_self_practice_attempts`（`schema.py:492`）用 `status IN ('open','scored')` + 「重复提交不再计数」，说明「按次记录 + 状态机」是本项目既有做法，不是新发明。

## 5. 三个候选方案对比

| | 方案 A：改唯一键加版本列 | **方案 B：旁挂明细表（推荐）** | 方案 C：新表做权威，`submissions` 降级为投影 |
| --- | --- | --- | --- |
| 做法 | `UNIQUE(assignment_id,student_id,version)`，重建表 | 保留现表；新增草稿/版本/状态三表 | 新建权威提交表，旧表改为兼容视图 |
| 表结构改动 | 重建 `submissions` | **零改动** | 大改 + 视图 |
| 需改的读写点 | 9 / 16 | **1 / 16**（仅提交事务） | 16 / 16 |
| 静默错算风险 | 高（统计、画像翻倍） | **无**（旧查询语义不变） | 高 |
| 历史数据迁移 | 有（真库 0 行，但不保证别人环境为 0） | **无** | 有 |
| 回滚 | 需再重建一次表 | **删三张新表即回滚** | 几乎不可回滚 |
| 与设计文档一致性 | 一般（文档明写「优先用关联的设置或明细结构，避免加列破坏旧接口」§5.2） | **一致** | 不一致 |
| 未来扩展（量规、复核历史、订正） | 受限在单表 | 明细表天然可挂更多列 | 灵活但重构代价大 |

方案 B 的最大好处不是「省事」，是**把风险隔离在新增面**：老接口行为不变，统计口径不变，出错只可能错在新功能上，回滚成本接近零。

## 7. 推荐方案 B 的具体设计（待确认后实现）

### 7.1 三张新表（全部 additive，不动 `submissions`）

```sql
-- 1) 草稿：一人一任务一行，可反复覆盖，不产生成绩
CREATE TABLE IF NOT EXISTS training_submission_draft (
  assignment_id TEXT NOT NULL REFERENCES assignments(id),
  student_id TEXT NOT NULL REFERENCES users(id),
  answers_json TEXT NOT NULL,          -- 学生选择（明文，与 submissions.answers_json 同口径）
  saved_at TEXT NOT NULL,
  PRIMARY KEY (assignment_id, student_id)
);

-- 2) 历史版本：append-only，每次正式提交一行（含被替换的那一次）
CREATE TABLE IF NOT EXISTS training_submission_version (
  id TEXT PRIMARY KEY,
  assignment_id TEXT NOT NULL REFERENCES assignments(id),
  student_id TEXT NOT NULL REFERENCES users(id),
  version INTEGER NOT NULL,            -- 1,2,3...
  answers_json TEXT NOT NULL,
  score REAL NOT NULL,                 -- 自动判分
  details_json TEXT NOT NULL,          -- 加密列（需注册 REGISTRY）
  adjusted_score REAL,                 -- 该次的人工复核分（历史保留，不随重交清空）
  feedback TEXT,                       -- 加密列
  reviewed_by TEXT REFERENCES users(id),
  reviewed_at TEXT,
  kind TEXT NOT NULL DEFAULT 'submit' CHECK (kind IN ('submit','correct')),
  submitted_at TEXT NOT NULL,
  UNIQUE (assignment_id, student_id, version)
);

-- 3) 学生进度状态：两层状态里的「学生这一层」
CREATE TABLE IF NOT EXISTS training_submission_state (
  assignment_id TEXT NOT NULL REFERENCES assignments(id),
  student_id TEXT NOT NULL REFERENCES users(id),
  status TEXT NOT NULL DEFAULT 'not_started'
    CHECK (status IN ('not_started','in_progress','submitted','pending_review','returned','done')),
  attempts INTEGER NOT NULL DEFAULT 0,     -- 已正式提交次数
  return_reason TEXT,                      -- 教师退回原因（加密列）
  returned_by TEXT REFERENCES users(id),
  returned_at TEXT,
  correct_due_at TEXT,                     -- 订正期限
  updated_at TEXT NOT NULL,
  PRIMARY KEY (assignment_id, student_id)
);
```

### 7.2 提交事务时序（改一处：`storage.save_submission`）

同一 `BEGIN IMMEDIATE` 内完成，任一步失败整体回滚：

1. `check_submission`（保留）＋ **新增**：已交次数 `< submit_limit`，否则 409「已达提交上限」。
2. 若 `submissions` 已有行 → 把它整行**快照**进 `training_submission_version`（版本号 = 现有次数 + 1），保留当时的 `adjusted_score / feedback / reviewed_by`。
3. 执行原 `upsert` 写当前提交（清复核的语义保留 —— 因为历史已存住了）。
4. `training_submission_state`：`attempts += 1`，`status = 'submitted'`（无需人工复核的客观题可直接 `done`）。
5. 删除该任务的草稿行。
6. 原 `mistake_book.capture` 与 `_log` 保持。

### 7.3 加解密注册（必须做，否则读历史版本会抛「完整性校验失败」）

```python
'training_submission_version': (('assignment_id', 'student_id', 'version'), ('details_json', 'feedback')),
'training_submission_state':   (('assignment_id', 'student_id'), ('return_reason',)),
```

`verify_state`（`sensitive_storage.py:156`）只校验 state 表、不遍历 REGISTRY，因此**新增注册项对既有数据无影响**，无需迁移。

### 7.4 接口（扩展既有语义，不新开并行主线）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/assignments/{id}/draft` | 取草稿（无则 204） |
| PUT | `/api/assignments/{id}/draft` | 保存草稿，带 `saved_at` 回执 |
| GET | `/api/assignments/{id}/versions` | 本人历次提交（学生）/ 某任务全班（教师，带 student 过滤） |
| POST | `/api/assignments/{id}/return` | 教师退回：必填原因 + 订正期限 |
| PUT | `/api/assignments/{id}/review` | 现有复核，改为写 `submissions` 同时回填版本表对应行 |

`/api/assignments/{id}` 的返回体新增 `draft`、`attempts`、`submit_limit`、`status`、`return_reason` 五个字段（**只加字段，不改老字段**）。

**实测确认缺陷已修**（同一探针）：

```
1st submit: 200 | 2nd submit: 409          ← 重复提交被拒
after review adjusted_score: 88.0
3rd submit after review: 409
adjusted_score after resubmit: 88.0         ← 复核分不再被抹掉
```

三条需要记在案的决定：

1. **`retake_policy` 默认 `teacher_return`**（按第 6 节口径 1）。历史「覆盖式重交」通过
   `retake_policy='free'` 显式保留，任务设置里可切换。
2. **改了 6 个历史用例的夹具**：`test_classroom` / `test_mistake_book` / `test_training_stats` /
   `test_training_profiles` / `test_exercise_generator` 里断言「重交覆盖」的用例，加了
   `allow_free_retake()` 显式选择旧口径；`test_classroom` 另加 `open_answers_after_submit()`
   （该用例断言提交回执里的机器分，截止在 2032 年，默认 after_due 会被策略挡掉）。
   断言本身没改，只是让它们不再依赖「重交无闸门 / 交后必给分」这两个默认值。这是口径变更的必然结果，不是放宽测试。
3. **顺带修掉的真缺口**：`settings_for` / `answer_policy` 原来以 `training_assignment_settings`
   驱动 LEFT JOIN，单独点发给某个学生的作业在这一表里没有行，配好的策略取不到（等于旁挂表形同虚设）。
   现改为 `task_row()`：查不到登记行就退回作业自身的 `training_task_settings` 行。
4. **内容版本冻结的三条口径**（2026-10-22 追加，用户选「发布时存冻结快照、提交关联快照 id」）：
   - 只有**已发布**任务才冻结；未发布任务 `frozen` 为 `None`。历史已发布任务在首次读取时补冻。
   - 冻结内容 = 题目材料指纹 + 关联规则快照 id + 考纲内容版本 + 答案开放策略，sha256 指纹相同就不新建（幂等）。
   - 提交时 `training_submission_state` 记**当下**快照；被覆盖的那次归档进 `training_submission_version`
     时记的是它**当初判分**的快照（从 state 里带过去），所以历史记录不随公共知识更新漂移。
   - `drift()` 只报告「规则快照已变，如需采用新口径请新建任务」，**不自动轮换**已发布任务的内容。
