## 一、背景与目的

TaxPearls 现有能力覆盖"财税审计实训 + 代账作业台"两个出口。新的业务方向要求面向高校客户提供：

1. **高校管理端**：院校级的教学组织管理能力（院系、专业、班级、学期、课程、师生管理）；
2. **代码实训自动评分**：学生提交代码、系统自动判题评分的教学能力。

现有产品的实训评分（PRD 模块 E）建立在"规则库反向出题 → 风险点集合比对（命中/漏检/误报）"之上，不涉及执行学生提交的代码。因此本文的核心判断是：**高校管理端是对现有平台层的结构扩展，代码实训自动评分是与现有规则引擎并列的全新能力域。**

## 二、分析范围与方法

- 输入：docs 目录五份文档（00、01、02、03、05）所载系统现状、需求状态与约束。
- 判定口径：某能力"可直接复用"指现有实现无需结构性改动即可服务新场景；"需扩展"指现有实现提供骨架但必须增加新模型或新逻辑；"未覆盖"指现有文档与代码均无对应设计。
- 本文只做差距识别与模块划分，不含技术选型结论与排期；选型与排期见第九节待确认事项。

## 五、差距 A — 高校管理端

现有"机构 → 班级"两层模型可承载单院系试点，但无法表达高校的真实组织结构与管理需求。本域缺口集中在**组织结构与管理视角**，平台基础设施（账号、权限、通知、安全）均有骨架可依。

| 编号     | 缺口                                              | 现状对照                                                        | 判定  |
| ------ | ----------------------------------------------- | ----------------------------------------------------------- | --- |
| FR-U01 | 高校组织架构：院系 / 专业 / 班级 / 学年学期 / 课程的多层模型，班级按学期重建与归档 | 现有仅机构 → 班级两层；PRD 2.2 角色定义无院系概念                              | 未覆盖 |
| FR-U02 | 校级管理员角色：跨院系查看教学概况、分配教师与班级、统筹考核                  | 权限矩阵（PRD 2.3）仅教师/学生/机构管理员/会计/平台管理员；"机构管理员"语义是代账负责人，不是校级管理视角 | 未覆盖 |
| FR-U03 | 师生批量导入（Excel 名单）、账号与班级的批量绑定、学期初整建制的班级迁移         | 现有邀请制为逐人邮箱邀请，席位按机构配额（默认 5 席，可选 20/50 席），不适合千人级院校            | 未覆盖 |
| FR-U04 | 课程管理：课程与教师、班级、学期绑定；同一课程多班平行开课；课程级作业序列           | 现有作业直接挂在班级上，无课程实体                                           | 未覆盖 |
| FR-U05 | 高校端管理报表：院系/专业/课程维度的教学统计聚合（现有学情统计只到班级与作业维度）      | `webapp/training_stats.py` 口径为"当前有效名册 + 最新有效提交"，按班级聚合       | 未覆盖 |
| FR-U06 | 席位与配额模型调整：院校按师生总数配额，而非现有小型席位档位                  | 现有席位 5/20/50 档与并发核销逻辑面向代账机构                                 | 需扩展 |

## 六、差距 B — 代码实训自动评分

这是与现有规则引擎**并列的全新能力域**，不是模块 E 的参数化扩展。根本差异：现有评分是对"风险点集合"做确定性比对（学生标注 vs 规则库标准答案），代码评分必须**执行学生提交的不可信代码**并与测试用例比对——这一步在现有架构中完全不存在（03 号文档明确规则引擎"不执行 Python、eval、SQL 或任意代码"，05 号文档的部署模型也未考虑运行用户代码的隔离面）。

| 编号     | 缺口                                                         | 现状对照                                                                     | 判定  |
| ------ | ---------------------------------------------------------- | ------------------------------------------------------------------------ | --- |
| FR-J01 | 编程题库数据模型：题目、测试用例（输入/期望输出/权重）、判题配置、语言与运行环境版本、题目与现有班级作业实体的关联 | 模块 E 全部围绕"规则反向出题"的财税查账题；`src/exercise_generator.py` 由规则生成仿真账套，与编程题无关     | 未覆盖 |
| FR-J02 | 代码提交与版本存储：多次提交历史、每次提交的判题结果版本、代码文件管理                        | 现有提交实体是"风险标注答案"，关联教学提交加密载荷；无代码文件概念                                       | 未覆盖 |
| FR-J03 | **判题沙箱**：隔离运行不可信代码的执行环境（容器池、CPU/内存/时间/网络限制、文件系统隔离）         | 现有 Dockerfile 面向应用自身部署（非 root、固定依赖、中文字体）；模块 F 安全需求中无"执行用户提交代码"条目，属全新高风险面 | 未覆盖 |
| FR-J04 | 判题引擎：编译、逐测试用例运行、输出比对（含浮点容差、多解判定等策略）、部分得分、超时/运行错误/编译错误的分类归因 | 现有确定性求值只有 deviation / amount_mismatch / ratio_range / all 四种，面向指标比对      | 未覆盖 |
| FR-J05 | 判题任务队列与并发调度：大量学生同时提交时的排队、判题机调度、失败重试与状态机                    | 01 号文档明确本机分析并发"按单进程执行，多副本部署须另行验证"；无异步任务队列                                | 未覆盖 |
| FR-J06 | 代码查重 / 抄袭检测：班内与跨班同题比对                                      | 现有教学诚信控制仅有"仿真材料红线"校验                                                     | 未覆盖 |
| FR-J07 | 代码质量维度（可选）：lint、规范、复杂度等辅助评分项                               | 未覆盖                                                                      | 未覆盖 |
| FR-J08 | 判题结果与现有评分体系对接：判题产出作为评分框架的客观事实来源，沿用评分标准配置、教师调分、评分明细与留痕      | `src/training.py` 评分框架可承接，但"事实来源"接口需从规则引擎结果抽象出来                          | 需扩展 |

## 七、新增模块汇总

| 新增模块                | 承接的缺口          | 与现有系统的关系             |
| ------------------- | -------------- | -------------------- |
| 高校组织模型（院系/专业/学期/课程） | FR-U01、U04     | 平台层结构扩展，需迁移或兼容现有班级实体 |
| 高校管理端角色与视图          | FR-U02、U05     | 权限框架内新增角色与聚合报表       |
| 师生批量导入与配额调整         | FR-U03、U06     | 邀请制旁路新增导入入口，席位模型参数化  |
| 编程题库与测试用例管理         | FR-J01         | 全新数据模型               |
| 代码提交与判题记录           | FR-J02、J04、J08 | 全新执行链路；结果回填现有评分框架    |
| 判题沙箱与任务队列           | FR-J03、J05     | 全新运行面，涉及部署与安全扩展      |
| 代码查重与质量评分           | FR-J06、J07     | 判题链路的可选增强            |

优先级建议（仅依据依赖关系，供决策）：

1. **先通判题最小闭环**（对应 P0 铁律："先把可举证的路打通，再往上堆"的同等逻辑——先让一道编程题从提交到判题到评分明细走通，FR-J01/J02/J03/J04/J08）；
2. **再上高校组织模型**（FR-U01/U02），因为判题闭环可在现有班级实体上验证，不被组织模型阻塞；
3. **批量导入与并发判题**（FR-U03/J05）随真实课堂规模接入；
4. 查重与质量维度最后补全。

## 八、与现有约束的衔接

- **分支归属**：本差距分析文档置于 `university-extension` 分支。后续实现建议：高校管理端 → `university-extension`（或按其稳定业务目的再拆）；代码判题业务 → `teaching-training` 或新建 `code-judge`；判题沙箱的基础设施与部署部分随业务分支或归 `deployment-ops`。两域互不依赖，可独立交付。
- **安全扩展**：模块 F 需新增"不可信代码执行"类需求（沙箱隔离、资源限额、逃逸防护、判题日志），并按 05 号文档要求为新模块敏感字段（代码提交、判题记录、师生名单）同步适配列级加密。师生批量导入涉及个人信息，纳入 FR-F03 字段加密范围。
- **验收边界延续**：本文沿用现有文档口径——需求条目不等于已实现；沙箱与教学只用仿真/教学数据；真实课堂、生产部署与判题沙箱的安全验收各自单独进行，不以本地验证代替。
- **报告与证据口径**：代码判题结果若需出教学报告，沿用"每分必有所据"原则（FR-E05 同等要求）：每个测试用例的通过/失败、得分、归因均可展开核对。
