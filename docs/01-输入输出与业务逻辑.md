# 税海拾珠 · 输入输出与业务逻辑

## 基础业务输入与数据处理（规则核验前）

企业“上传材料”页面默认提供基础资料处理任务：先填写企业名称、税号和检查起止日，复用同机构有权访问的企业档案；再分别上传科目余额表（Excel）、增值税申报主表及实际适用附表（Excel/PDF）、进销项发票明细（Excel/XML）。同类资料可多文件上传，同名文件各有独立来源ID。银行流水、凭证、总账及企业信息附件不作为此任务的必传材料。

```text
企业与检查区间 → 三类上传槽位 → 实际格式检查和原件加密保存
→ 业务字段映射 → 标准记录及字段位置 → 企业/期间/资料完整性核对
→ 有来源的区间数据与原值汇总 → 等待规则核验
```

此入口不执行税务规则、不调用AI进行风险判断、不生成报告。API 为 `/api/enterprise/input-tasks`；任务详情保留文件、标准记录、原始行/节点、字段来源、金额缺失状态、期间覆盖缺口和版本记录。旧材料检测接口拒绝对此类任务确认执行。

“下载标准数据 JSON”通过 `/api/enterprise/input-tasks/{task_id}/data?expected_revision=版本号` 导出 `taxpearls.material-data.v1`，顶层仅有 `schema_version`、`task`、`records`、`sources`：包含检查对象与期间、按材料类型预留的业务字段、原始单位及期间口径、字段原值/位置/OCR引文和已确认口径。金额保持十进制字符串，票号等标识保持文本，未知值为 `null`；每条记录的 `quality` 仅保留字段缺失/无效状态、来源是否待核实、是否在检查区间及重复记录关联。页面的核对提示、覆盖缺口、处理说明、严重程度和次数均不进入提取数据 JSON；原有任务详情继续保留并展示这些检查结果。导出数据本身不宣称整期资料齐全或可以开展分析，空记录仍为 `[]`；现有 AI 核查继续按原有证据包和完整性检查执行。导出不包含整段原始行、任务历史、操作事件、租户信息或模型配置；原件和完整处理历史继续在系统内留存。下载受任务权限、版本及未保存编辑检查约束，不会触发 AI 调用。

已知字段别名按业务类型映射；用户可授权未知表头由已有模型服务补充映射，只发送表头与样例值形态。候选映射限定机构、业务类型及上下文；五个不同原件哈希的一致结果可复用，重复解析/上传不增加次数，有冲突则不晋升。映射学习和税务规则、政策图谱分离。

同一原件哈希已验证的候选映射可在刷新、补传和本地重新整理时继续使用，关闭新的AI请求不清除既有映射。此复用仍限定机构、业务类型及上下文，不增加独立次数；未满五次的候选不能直接复用于另一原件。

网页字段映射和扫描PDF识别使用管理员配置的“材料提取兜底”用途模型及兼容备用密钥，与现有材料提取入口保持一致；不借用分配给知识问答、报告或教学答疑的专用配置。

余额表保留科目汇总而不伪造逐笔交易。申报表保留主附表、栏次及金额列口径；季度数不复制为每个月的数值。发票按开具日期进入区间视图；区间外记录继续保留。同票不同值提示冲突，重复来源不重复统计；红字和作废状态分组展示原值，不自行推定税务调整。金额使用十进制文本保留精度、原单位；空白不等于零。发票日期跨度不作为资料覆盖完整的证明。

无法从文件独立核验税号时明示来源限制；发票按进销项角色核对本企业一侧税号。不能识别单位或期间时可填写人工核对信息并保留其来源标记；与文件明确记载的口径冲突仍阻止就绪。实际适用附表清单须按本企业本期情况明确确认，程序没有预设所有企业统一清单。

文本PDF优先读表格；无法提取的页可另行授权发送页图到已配置模型OCR。OCR候选保留页码、栏次及引文，需要对照原页核对；结构无效、数值无引文或空字段不会默认为有效数据。XLS支持固定值BIFF5/7/8，包含Excel 97–2003；兼容已核验的Excel/WPS扩展信息，静态批注和绘图保留在原件但不取数。含公式、宏、活动嵌入对象、外部引用或其他不支持部件的文件会明确提示。复杂非标准表头、扫描质量及实际XML格式需以真实企业样本进一步验证，不能由合成测试宣称全面兼容。

2026-10-13本地浏览器验收使用临时数据库和仿真三件套，连接真实DS服务。覆盖登录建任务、缺项阻止就绪、非标准表头映射、补齐进项、重复原件不重复计数、刷新后本地整理保留候选、扫描PDF取数与原页核对、错企业拦截及排除、原件下载字节一致和整理JSON下载。修复后完整复验使用4次字段映射和1次OCR，均成功，最终资料就绪且缺口为0；25项核心回归通过。此结果不代表真实外部账套、全部XML格式或线上部署验收。

```text
登录 → 上传材料 → 核对主体与指标 → YAML 规则求值 → 证据卡 → HTML / A4 PDF
```

## 输入约定

### 企业基础审查的核心上传材料（2026-10-11 已确认）

企业基础审查用于核对账面、申报和开票数据，必须提供以下三类材料，均属于同一家被检测企业、同一个主检查期间：

| 必须上传的材料 | 内容要求 | 主要上传格式 |
| --- | --- | --- |
| 科目余额表 | 科目名称、期初余额、本期借方、本期贷方、期末余额；原件提供科目编码时一并保留 | Excel：`.xlsx` / `.xls` |
| 增值税申报表及相关附表 | 主表及与检查有关的附表，包含销售额、销项税额、进项税额等申报数据 | Excel：`.xlsx` / `.xls`，或 PDF：`.pdf` |
| 销项、进项发票明细 | 批量明细，保留票号、开票日期、金额、税额及红字、作废状态；必须提取买卖双方的公司名称和纳税人识别号供归属核对 | Excel：`.xlsx` / `.xls`，或数电发票 XML：`.xml` |

- 三类均为必需材料；缺少任何一类，账面—申报—开票基础审查的材料不完整。缺失材料不能按零业务或检查通过处理。
- 企业名称、纳税人识别号和主检查期间必须明确。发票中的公司名称和税号可用于预填企业身份；用户确认被检测企业，信息明确时无须重复手填，也不要求额外上传企业信息文件。主检查期间另行确认，不能把一张发票的开票日期当作完整检查期间。
- 发票优先使用批量明细或数电发票 XML，不要求逐张上传照片。银行流水、合同及履约材料、三大财务报表和工资社保按具体检查需要补充，不作为每次基础审查的统一必需项；补充材料同样受本次检查时间范围约束。
- 核心材料齐全不代表所有规则都可执行；补充数据不足时，相应检查仍标为未执行，并说明缺项。

**读取与 JSON 整理路径**：Excel / XML 直接读取并整理为统一 JSON；文字型 PDF 先提取文字和表格，再整理为 JSON；只有扫描件或图片时，采用“扫描 PDF / PNG / JPG / JPEG / TIF / TIFF → OCR / 图像识别 → JSON 候选 → 对照原件核对确认”的备用路径。JSON 保留材料类型、企业与期间、原始值、单位及来源位置，由系统生成，用户上传原始材料即可。识别、单位换算和字段映射须核对，缺失值不补零。

#### 发票企业身份提取与进销项归属（2026-10-11 已确认）

发票 JSON 必须分别保留 `buyer_name`（购买方名称）、`buyer_taxpayer_id`（购买方税号）、`seller_name`（销售方名称）、`seller_taxpayer_id`（销售方税号），并保留各字段的原始内容及原件位置。缺失或无法辨认的字段留空并提示核对，不能由公司名称猜出税号。

先从材料提取企业身份候选，再由用户确认被检测企业或选择已有企业；不能把某张发票的购买方或销售方自动指定为被检测企业。多个企业候选需要明确选择，原文之间或与已选企业信息冲突时提示核对，不覆盖用户已填写、确认的信息。

以已确认的被检测企业税号为准，税号按已有规范归一后精确匹配；名称用于展示及辅助核对，不作为唯一归属依据：

| 税号匹配结果 | 发票归类与处理 |
| --- | --- |
| 仅销售方税号匹配被检测企业 | 归为该企业销项发票 |
| 仅购买方税号匹配被检测企业 | 归为该企业进项发票 |
| 两方均不匹配、两方均匹配，或关键身份字段缺失、冲突 | 标记待核对，保留原件和记录，暂不计入正式归集 |

进销项归类只确定交易方向，不自动证明购进发票可以抵扣；抵扣用途、期间和确认状态仍须另行核实。

#### 检查时间跨度处理（2026-10-11 已确认，待实现）

- **范围由用户规定**：上传前选择月份、季度、年度或明确起止日期；统一记录检查开始日和结束日。程序读取材料时间用于核对，不能按已有材料的最早/最晚日期自行决定范围，也不能用扫描结果改写用户选择。
- **所有材料受同一范围约束**：核心材料与补充材料的实际所属期或业务日期均须在所选范围内，日期包含起止日。范围外历史参考和跨期证据不作为本次检查的例外输入；含范围外记录的混合文件须提示重新提供符合范围的材料，不静默过滤或混入本期数据。
- **按材料类型读取时间**：科目余额表、申报表按原文所属期核对；发票按开票日期核对；银行流水按交易日期核对。单个报表时点不能证明完整业务期间。合同等含签订、履约等多个日期的材料，仍须按检查用途明确判定字段，不能任选一个落在范围内的日期就放行。
- **未知和冲突先处理**：无法识别、OCR 不确定、跨出范围或来源之间冲突时标记待核对，未经处理不能纳入正式检查。原文日期、原文位置、用户所选范围和核对状态分别保留；手工填写范围不等于证明材料日期，不以文件名、上传时间或修改时间代替业务时间。
- **变更范围重新核对**：用户修改起止日期后，重新检查已有材料及确认状态，保留原件和已冻结结果，不直接沿用旧范围的确认。

现有程序仍有历史参考及多期间处理能力，下文对此的说明记录既有实现；本次新业务要求以用户所选范围内的核心和补充材料为准，相关行为待对齐和验证。任务已在 [功能待办](../TODO.md) 标记，未实施程序改动。

#### 核心材料 JSON 字段（2026-10-11 已确认，待实现）

第一版确认以下五组业务字段。JSON 由系统按材料类型生成，用户上传原件；字段先完整预留，读取不到时保留为空并说明原因，不能因为 JSON 中存在字段名就认为数据可用。补充材料的具体字段另行逐项确认。

| 字段组 | 应保留的字段 | 业务作用 |
| --- | --- | --- |
| 本次检查信息 | 被检查企业名称、税号、用户选择的检查开始日期和结束日期 | 确定检查对象和范围；与材料原文提取的信息分别保存，用于发现冲突 |
| 每份材料的公共信息 | 材料类型、原件企业名称与税号（有则提取）、原件所属期或业务日期、币种、金额单位、文件编号和文件名、来源位置、提取方式、核对状态 | 确认企业、期间、金额口径与来源；来源位置具体到 Excel 工作表/单元格、PDF 页码/位置或 XML 节点 |
| 科目余额表 | 科目编码、科目名称、期初余额及借贷方向、本期借方发生额、本期贷方发生额、期末余额及借贷方向；原件提供的上下级科目关系 | 提取账面收入、成本和税额，避免上下级科目重复相加；原件借贷分列时分别保留，不猜测余额方向 |
| 增值税申报表及相关附表 | 表名、所属期、行号、项目名称、原始列名、金额；原件明确载明的纳税人类型 | 定位销售额、销项税额、进项税额、应纳税额、期末留抵等项目，区分本期/累计及主表/附表的不同口径 |
| 发票明细 | 发票号码、开票日期、购买方名称及税号、销售方名称及税号、发票类型、不含税金额、税额、价税合计、红蓝字标识、有效或作废状态 | 按企业税号确定进销项归属，核对重复发票，计算有效发票金额；红蓝字与有效/作废状态分开保存 |

**按原件和检查需要填写的字段**：

- 发票代码、红字对应的原发票号码：原件有则保留，没有时不补造。
- 商品或服务名称、税率、各明细行金额与税额：原件有明细时逐行保留，只有汇总数据时不生成虚构明细。
- 抵扣用途、确认状态、抵扣所属期、进项转出状态及税额：预留这些字段，抵扣相关检查按实际依赖核验；缺失或未确认时，不将购进票面税额当作已确认可抵扣税额。
- 申报版本或更正状态：来源有则保留，用于区分同一期间的原申报和更正申报；版本冲突须核对，不能重复使用。

**原件字段、计算结果与缺失处理**：

1. 原件提取值与系统计算值分开保存。发票买卖双方税号属于原件字段，进销项方向属于税号匹配结果，销项发票金额合计属于计算结果；匹配和计算结果须记录依据、所属期及对应输入记录。账面指标按明确的科目映射计算，未知科目不能猜测归类。
2. 每个关键字段保留原始内容、整理后的候选值和原件位置，确认采用值与候选值区分。修改时记录修改前后值、操作人和时间，不改写原件。金额同时保留原始单位与换算依据；票号、税号和科目编码按字符串保存，金额采用十进制计算，JSON 金额用十进制字符串表达。
3. 本次被检查企业和检查范围必须明确；材料企业归属、期间或关键来源存在未解决的问题时先核对。具体检查是否可执行，依据其所需字段及有效性判断，不要求所有预留字段都必须非空，也不把缺失值填成零。明确记载的零值有效，缺失值记为 `null` 并说明原因；数据不足的检查显示“未执行”及缺项。

这五组字段用于建立“账面—申报—开票”基础核对，不代表三类材料齐全后所有规则均可执行；其他检查仍按所缺证据补充材料。

#### 科目余额表与补充明细账的格式范围（2026-10-11 已确认，待适配验证）

科目余额表以 `.xlsx` 为主要格式、`.xls` 为兼容格式；按需补充的明细账以 `.xlsx` 为主，纳入 `.csv` 结构化记录，PDF 和扫描件为备用路径。以下是本次确定的支持目标，不代表所有后缀、来源和版式已经能正确识别；其他核心材料仍沿用前述格式约定。

| 文件格式 | 定位与用途 | 处理要求与当前边界 |
| --- | --- | --- |
| Excel `.xlsx` | 科目余额表、明细账的主要格式 | 直接读取实际表格中的表头、记录和源单元格，按版式映射字段；已有部分余额表读取能力，明细账分类、对账及新取数口径仍待开发验证 |
| 旧版 Excel `.xls` | 余额表、申报表兼容格式，明细账按样本适配 | 支持固定值 BIFF5/7/8（含 Excel 97–2003），保留中文表名、合并格及来源位置；已核验两份真实 BIFF8 申报模板可读取。不执行公式、宏或活动对象，其他来源和版本仍按实际样本核验 |
| CSV `.csv` | 补充明细账的结构化格式 | 明确字符编码、分隔列和数字表示；文件内容或同批次可追溯原件须能证明企业、期间、字段和单位，缺失先核对。已有其他表类的 CSV 路径不等于明细账已适配，不由文件名或上传时间补造归属和期间 |
| 文字型 PDF `.pdf` | 无可用电子表格时的备用材料 | 提取文字和表格，核对页码、行列、金额、期间及跨页表头；现有部分 PDF 报表读取不代表余额表、明细账全部版式可用 |
| 扫描 PDF、JPG、PNG | 扫描件备用材料 | OCR / 图像识别生成候选并对照原件确认；不把识别成功等同于取数正确，专用 OCR 与这些表类的完整处理仍待适配验证 |

第一版优先适配三种表格结构：单层表头；“本期发生额”下分借方、贷方等多层表头；总科目与明细科目同时存在且层级明确的结构。多层表头须结合上下层定位，同名栏次不唯一时提示选择；层级不明时不自动汇总，父子金额不能重复计入。

文件类型和软件导出版式分开确认：具体财务软件、版本和导出方式按实际原件样本验证，不能宣称支持某一品牌就覆盖其全部导出。表内图片、嵌入报表对象或无法明确行列关系的文件须单独适配，不因 `.xlsx` 后缀直接放行，也不通过改后缀或删除对象冒充已支持。未支持的结构明确指出缺口；需要重新导出时保留原件，以财务软件导出的可读表格核对，不要求用户逐项抄成系统模板。

本次只确认格式与优先版式范围，不安装 OCR、不新增解析器，不改变已验证能力的状态；真实余额表和明细账仍须按企业、期间、金额、业务口径、来源及完整性逐项验收。

#### 科目余额表字段对应与指标取数（2026-10-11 已确认，待实现）

按“原件列定位 → 原始科目记录 → 科目业务映射 → 口径核对 → 指标计算”处理。列名对应解决读哪个数；科目映射和口径核对决定这个数能用于哪项检查。按材料来源和版式配置明确的对应关系，同类格式复用；未知版式、同名重复列或科目含义不明时待核对，不由 AI 猜出正式映射。

| --- | --- | --- |
| 科目编码 / 科目代码 / 科目编号 | 科目编码 | 保留原编码，按字符串保存；不改成默认账套的编码 |
| 科目名称 / 会计科目 | 科目名称 | 保留原名称，作为科目含义核对依据 |

| 期末余额，及原件提供的借方 / 贷方或方向列 | 期末余额及借贷方向 | 反映期末时点，不能当作期间收入、成本或税额发生额 |

每行科目保留原件列名、层级、金额单位、实际期间及源单元格。行汇总与明细只能选择一种完整覆盖口径；例如总科目 100 万、两个明细 60 万和 40 万，取总科目或完整明细合计均为 100 万，不得合计为 200 万。层级不明、明细不完整、重复期间、缺科目或单位不明时，不生成貌似完整的指标。

**四项指标的业务口径**：下表规定用于核对的目标口径；借贷净额计算只适用于已经明确业务内容并排除损益结平、内部重分类等不属于目标口径的记录，不能对全部借贷发生额直接相减。红字负数按原始符号计入；已经在发生额中冲减的金额不能再次扣除。

| 指标 | 对应的业务科目 | 用于核对的金额 |
| --- | --- | --- |
| 账面营业收入 | 已确认的主营业务收入、其他业务收入科目 | 本期确认的不含税收入，计入本期退回、折让及收入更正影响；对已分类的业务发生额按贷方减借方归集，不计入转入本年利润的损益结平记录 |
| 账面营业成本 | 已确认的主营业务成本、其他业务成本科目 | 本期确认的营业成本，计入退回及成本更正影响；对已分类的业务发生额按借方减贷方归集，不计入转入本年利润的损益结平记录 |
| 账面销项税额 | 本企业实际“应交增值税—销项税额”明细或专栏 | 同期一般计税业务销项税额，保留退回、红字等冲减；销项税额抵减、待转销项、简易计税、缴纳及结转税款分别记录，不能把应交税费总额当销项税额 |
| 账面进项税额 | 本企业实际“应交增值税—进项税额”明细或专栏 | 同期该专栏的业务税额，保留退货、红字等冲减；待认证、待抵扣、进项转出等分别记录，账面进项与申报可抵扣金额的期间和口径另行核对，不能等同于购进发票税额合计 |

成本处理中须区分两种“结转”：库存商品等转入主营业务成本属于成本确认，须保留；收入、成本转入本年利润属于损益结平，不改变本期收入、成本。不能按摘要中是否出现“结转”两个字统一剔除，也不能把收入、成本的全部反向发生额都判为结平。

**什么时候需要补材料**：

- 科目编码与现有配置不同或缺少编码：先核对原件科目名称、层级及账套科目表；有明确依据后登记实际编码与业务科目的对应关系，保留原编码。仅凭名称相似不自动确认。
- 汇总表不能区分退回、折让、重分类与损益结平，或不能说明红字在发生额中的呈现方式：提示补对应科目在本次范围内的明细账及必要凭证，核对日期、科目、借贷金额、摘要、对方科目、凭证编号和来源。只有材料明确提供已按该口径处理的发生额并可追溯，或相关记录可据明细核实时，才采用结果；人工勾选本身不是处理依据。
- 进项、销项的细分口径不清：补对应增值税明细账；涉及抵扣确认、进项转出或其他调节时，再按具体检查补相应依据，不要求每次都上传整套补充材料。
- 已有保存数据完整、有效且符合本企业、本期间和本次口径时直接使用，不重复索要。材料不能证明某指标时，该指标保持待核对，依赖它的检查标为未执行；无关且条件齐全的检查仍可执行。

**直接采用、补明细账与人工核对的判断条件（2026-10-11 已确认，待实现）**：

由程序在输入分析阶段按事先定义的字段、映射和证据条件判断，不等待风险差异出现才检查取数依据，也不由 AI 自行决定必传材料。按下表顺序处理，先复用已经保存且适用的有效证据：

| 顺序 | 判断条件 | 处理结果 |
| --- | --- | --- |
| 1. 核对基本信息 | 表头无法唯一定位、企业/期间/单位冲突、科目映射或层级不明确、必要金额缺失 | 指出具体文件、位置及受影响指标，先核对相应信息；不靠改写用户检查范围或补零消除问题 |
| 2. 检查能否直接采用 | 基本信息有效、所需科目完整且无父子重复；原件及可追溯的导出说明能证明业务冲减已计入、损益结平等已排除，且取数范围与目标指标相同 | 直接采用该口径金额，保存原文/说明位置、映射、符号处理与计算依据；不重复要求明细账 |
| 3. 检查是否已有明细依据 | 余额表只有汇总数，不能证明目标口径，但系统已有本企业、本次范围内完整有效的相关明细及核对记录 | 复用这些记录进行分类和重算，不再次要求上传 |
| 4. 请求针对性补充 | 余额表不能证明目标口径，且没有足够的现存依据，例如收入借方无法区分退回与结平，或红字呈现方式不明 | 请求相关科目在本次检查期间的明细账；必要时再补具体凭证。只影响依赖该指标的检查 |
| 5. 处理仍不明确的记录 | 补充后仍缺少关键记录、不能分类或存在未解决冲突 | 展示原记录及疑点，人工对照依据核对；相关指标不能正式采用，对应检查未执行 |

“只有单侧发生额”“反向发生额为零”“期末余额为零”“与申报金额一致”以及人工勾选，均不能单独证明第 2 项条件；必须有能追溯到原件内容的口径依据。程序不知道汇总金额的业务组成时，应如实提示“无法证明”，不能宣称已经识别出某笔退回或结平。

补充提示包含受影响的检查和指标、具体科目、缺少的依据、所需期间、可接受材料及现有来源。例如：“账面收入核对所需的主营业务收入借方汇总无法区分退货与损益结平，请补本次检查期间该科目的明细账。”明细账优先 Excel，PDF/扫描件按既定提取和核对路径处理；字段至少覆盖记录标识、日期、科目、借贷金额、摘要、对方科目、凭证编号及来源，缺少分类所需内容时再补相应凭证。

明细记录结合科目及对方科目的已确认含义、借贷方向、凭证和业务依据分为三类：正常业务及业务调整计入计算；损益结平排除；无法明确归类的记录待核对。摘要只是辅助，不能只凭“结转”或“退货”字样定类，也不能仅按金额大小、正负或 AI 建议采用。人工确认须关联依据并保留操作记录；检查仍有未分类的相关记录时，不仅汇总已分类部分冒充完整指标。

明细账须证明取数覆盖完整本次期间和目标科目；按原件借贷符号归集的总额应与余额表同口径金额核对，缺失、重复或差额先处理。明细账用于解释和重算已有金额，不与余额表金额再相加；红字已在原金额中扣减时不再二次扣减。计算结果记录纳入、排除和待核对的记录及依据。

例：收入明细中销售收入贷方 100 万、退货借方 5 万、转入本年利润借方 95 万，业务收入为 100 − 5 = 95 万；先排除结平 95 万，再计算业务净额，不能用全部借贷差额算成零。补充、修正或变更分类后重新核对并计算，旧确认失效，已冻结结果和原件保留。本节是输入核对与补充的业务要求，程序与真实账套验收仍待完成。

**当前实现与本次要求的差距**：`src/config.py` 的标准模板默认按 `6001 + 6051` 贷方生成收入、`6401 + 6402` 借方生成成本，以 `22210105` 贷方和 `22210101` 借方分别生成销项、进项；`src/loader.py` 只是把选定发生额相加，不识别业务冲减、损益结平或抵扣调节。`src/financial_import.py` 已有部分列定位及按编码和名称显式核对的旧科目映射，也不能据此证明所有账套的口径正确。现有规则说明中的“剔除结转、核实抵扣口径”不能视为程序已经做到。以上新口径须后续同步字段、计算、依赖校验、规则输入说明及验证样本，本次不改计算代码或规则阈值。

**核实依据**：财政部[《小企业会计准则》附录：会计科目、主要账务处理和财务报表](https://kjs.mof.gov.cn/zhengcefabu/201111/P020111118325852734144.pdf)第 59、62 页区分收入退回、成本确认与转入本年利润；这里只用于说明这些业务的区别，不将其全部科目编码套用于其他会计制度。财政部[《增值税会计处理规定》](https://www.mof.gov.cn/gp/xxgkml/hjs/201612/t20161214_2512803.htm)说明相关明细科目及专栏应分别核算。具体企业的适用制度、纳税人身份、业务和期间仍须核对，不以这些材料中的历史税收条件直接判断本次抵扣资格。

**实施边界**：以上是本次确认的企业基础审查业务要求。本次仅更新文档，三类材料齐全校验、核心材料统一 JSON 字段及提取/计算分离、科目业务映射与取数口径核对、发票身份预填/归属流程、统一检查时间跨度处理，以及各格式的实际识别能力仍须在程序中对齐和验证；允许上传某种后缀不代表任意来源、版式均可识别，旧版 XLS 仍受现有适配限制。

## 多源材料与业务勾稽

- 多期间：利润表发生额按期间归集，完整月份可生成滚动 12 月指标；资产余额按期点比较，不跨月相加。
- 数电发票：解析 XML 或标准发票明细，校验企业、期间、票号、红字及作废状态。票面税额不能直接当作申报表或账面税额。
- 银行材料：解析银行流水，结合经复核的银行调节底稿形成收入口径；未复核、缺底稿或重复调节不自动计入。
- 人力记录：按人员身份、月份和有效状态去重，归集工资与社保等人数口径；人数缺项不推测。
- 合同履约：通过合同台账、履约记录和四流勾稽表关联合同、发票、银行流水及履约单据，校验金额、期间与复核状态。

企业材料按单企业、单主期间持久化分析和确认。原件留存上传字节与指纹，补传、修正和重检形成新版本；兼容教学草稿仍在进程内存中。

Excel 与多文件解析共用工作簿、期间和输入错误处理。比较指标要求期间完整且口径可比；发生额按覆盖期间归集，时点余额只按对应时点读取。AI 提取结果作为候选数据进入校验，不自动替代缺失来源或人工确认。公共快照序列化工具保留数值、来源和关联关系，供报告与业务流程复用；读取已保存的审计快照不重新执行规则。

## 材料来源与归集口径

标准账表、来源适配与人工候选核对是不同入口。标准模板按约定表头读取，来源适配只覆盖明确支持的格式；不能因为后缀为 Excel、XML 或 PDF 就宣称内容均可识别。

| 来源              | 归属、期间与金额口径                                    | 缺项及冲突处理                                       |
| --------------- | --------------------------------------------- | --------------------------------------------- |
| 发票电子数据          | 区分买卖双方与被检测企业，保留票号、单据日期、红字和作废状态；票面税额不等于账面或申报税额 | 核对重复票与来源，不把同一发票跨文件重复计入；未知结构与无法核对的归属须复核        |
| 银行流水与调节底稿       | 区分本方账户、交易对方与业务期间；现金收支只有结合经复核的调节依据才能形成相应收入口径   | 缺底稿、重复调节或未复核记录不能自动计入；有稳定流水编号时据此去重，不凭金额相同认定重复  |
| 利润表、资产负债表、现金流量表 | 金额、单位、报表时点、发生期间与来源位置分别保留；发生额按覆盖期间归集，时点余额不跨期累加 | 不把单位不明、期间不全或不可比的值用于趋势；冲突不自动覆盖或相加              |
| 人力与合同履约材料       | 保留人员/合同/记录编号、有效状态、实际期间与依据；工资、社保、履约、发票和资金分别归集  | 缺项、未复核与重复记录保持可见，不猜测缺失金额，不把缺证据判为一致             |
| PDF 与非标准候选      | 可识别文本与模型输出均为候选，保留原文位置、金额和单位，人工核对后使用           | 扫描、读取失败、字段不存在与单位未知分别处理；模型不能补造事实或以票面值代替申报/账面指标 |

发票异常处理（FR-A07）：同一文件或跨文件的重复票号均阻止确认，列出两处源位置，不能自动按文件顺序选择状态或静默去重。仅明确的红字发票按一次负向计入票面净额；红票可使用全正或全负导出金额，金额、税额与价税合计符号须一致。“已红冲”“部分红冲”等原蓝票状态不能证明该行是红票，保持阻断并要求核对独立蓝/红明细，不自动把蓝票反向扣减。作废票不计金额，但在同方向汇总的剔除依据中保留原行；没有有效票的表不据此证明完整期间净额为零。数电 XML 若声称作废，须核对票种与实际红字明细，不自动接受其作废状态；电子发票不能作废、须按规定开具红字发票，依据见[税务总局说明](https://www.chinatax.gov.cn/chinatax/n810356/n3010387/c5242609/content.html)。

来源导出的抵扣指标须有明确确认、抵扣用途及本期所属期，不从“不抵扣”等包含相同字词的状态推断用途；转出标志与金额须一致，已转出却缺金额不能按零处理。既有六列标准模板的仿真抵扣约定保持兼容，不当作真实来源确认依据。购销双方原文税号与方向矛盾不能由方向文字或工作表名称覆盖；数值型长票号可能丢失精度，必须从来源按文本重新导出。程序不核验发票真伪、红冲对应关系或抵扣资格；红字确认单与已申报抵扣的转出属于另需业务依据的流程，见[税务总局红字数电发票说明](https://www.chinatax.gov.cn/chinatax/n810356/n3010387/c5236346/content.html)。旧发票批次的解析版本、源码与依赖不一致时，不能沿用可确认缓存；保存从加密原件重新读取，清除旧金额修正与复核，不发送模型，不改写原件或已冻结结果。

材料业务期间、单据日期、报表时点、导出时间、上传时间用途不同，不能相互替代。历史参考保留实际期间，不混入本期金额；与当前期间不匹配的材料须明确用途或排除。公开单组流程保存材料用途、分析与确认版本，原件使用独立密钥认证加密留存。

## 企业材料核对与输入分析

企业自用与机构多客户管理共用单组检测目标：一家被检测企业、一个主期间、多份文件。企业名称、税号和主期间起止日须明确；行业缺失如实提示，不编造行业。可识别且无歧义时从材料预填，不能用文件名、文件修改时间或上传时间替代企业归属或业务期间。

每份文件选择本期、历史参考或排除。历史参考必须属于同企业、明确实际期间且早于主期间，只进入支持的期间序列，不替换本期账表金额。原材料税号冲突、归属无法核对或本期期间不符仍须处理，手改企业字段不能消除冲突。

分析只检查输入完整性、冲突与规则是否具备可计算条件，不执行阈值判断或关联方风险结论。反馈分为必须处理、缺失但可继续、建议补充，并附涉及文件、影响和处理建议。读取失败不当成字段不存在，缺项不补零，零值仍是有效输入；分母为零或基期不足时列出不能执行的检查。

标准表数值修正仅接受允许的单元格，保留原值、修正值、来源位置和修正标记；候选账表重新解析与计算，原件不改写。非标准候选指标须人工核对，不允许用任意浏览器数据伪装服务端原文。字段修改不强制填写理由；操作人、操作时间与字段前后值由持久化版本和操作日志记录。

本地与 AI 提取保留材料指纹、来源位置、提取程序及依赖指纹。AI 请求还记录所请求模型、提示和结构指纹、请求次数及成功/失败状态；提供方未返回确切模型修订版时保持未知，不把请求模型名当成实际修订版。记录不包含密钥或环境变量，运行时间用于描述当次提取过程。

上述输入分析与修正已接入公开接口和单组页面。确认绑定企业、期间、文件、用途、修改和可执行范围快照；材料变化后重新分析和确认，补传重检形成新版本并保留先前结果。原件认证加密留存，访问控制和删除影响提示已接入，真实来源与生产密钥保管仍须单独验证。

## 账号与运行数据

登录采用限频和强口令校验。邮箱验证码、邮件链接和重置凭证限时、限次并绑定发起浏览器；链接需通过明确操作兑换，成功重置后注销已有会话。密码登录默认使用邮箱，同时支持用户名；优先匹配绑定邮箱，停用的邮箱账号不会回退到其他同名用户名账号。未勾选保持登录时会话为 12 小时，勾选后固定 30 天，Cookie 与数据库会话同步到期且不自动续期。退出只撤销当前会话，密码重置撤销该账号全部会话；密码不写入浏览器存储。

业务数据库通过 SQLite 在线备份接口在内存中生成一致性快照，并以 AES-256-GCM 认证加密后保存。恢复须停止服务，恢复前保留经过验证的加密安全副本。保留期由操作者明确选择，工具支持到期预览和单文件销毁回执；不自动删除备份。密钥只从进程环境读取，备份与密钥分别保管且不随代码提交。明文兼容命令须显式允许。

业务敏感字段使用独立的 `TAXPEARLS_FIELD_KEY`（32 字节随机密钥的 Base64），加密绑定表、列与记录身份；机构内等值查询使用带密钥的索引，索引不用于授权。缺失或错误密钥拒绝访问，已加密字段的明文或跨记录替换拒绝写入。已有数据库须停服执行离线迁移与压缩；认证加密恢复先验证字段内容，再替换目标。实际命令见 [运行说明](05-部署备份恢复与回滚.md)。

## 高校实训模块业务逻辑

面向高校客户的代码实训教学能力，需求定义见 [产品需求文档](02-产品需求文档.md) 第十一节，差距判断见 [高校端与代码实训差距分析](04-高校端与代码实训差距分析.md)。

用户角色：

| 角色      | 职责                                             |
| ------- | ---------------------------------------------- |
| 高校管理员 | 创建课程与班级，录入并发布代码实训任务，查看任务与评分报告 |
| 学生      | 查看所属班级的实训任务，提交源代码，查看本人评分报告   |

整体业务流程：

```text
管理员创建课程 → 创建班级 → 发布代码实训任务 → 学生查看任务、提交代码 → 系统沙箱运行代码 → 比对测试用例自动评分 → 师生查看评分报告
```

- 课程绑定名称、学期标注与任课教师，同一课程可多班平行开课；班级沿用现有「机构 → 班级」模型，绑定课程、任课教师与学生名册。
- 实训任务在课程班级下创建，包含题面、语言、时限与内存限制、测试用例、评分标准与截止时间；发布与名单沿用班级作业框架。
- 学生在截止时间内查看任务并提交源代码，可多次提交；每次提交独立存档，保留代码内容、提交时间与判题结果版本。
- 系统在沙箱中隔离运行提交的代码：单线程串行执行，一次一个判题任务；禁用网络，限制 CPU、内存、时间与文件系统写入，超限终止并归因。
- 判题逐测试用例运行并比对输出，支持浮点容差与空白容忍，按用例权重计算部分得分；编译错误、运行错误与超时分别归因。
- 判题结果作为客观事实来源回填现有评分框架，形成评分明细报告；师生按授权范围查看，评分标准可配置，教师调分留痕。

输入：

| 来源      | 内容                                                              |
| ------- | --------------------------------------------------------------- |
| 高校管理员 | 课程、班级、实训任务与测试用例（输入、期望输出、权重），以及评分标准与截止时间 |
| 学生      | 源代码提交，语言与运行限制随任务约定                                    |

输出：

- 任务列表：按课程与班级展示已发布实训任务、截止时间与提交情况。
- 代码运行日志：每次提交在沙箱内的编译与逐用例执行记录，含超限与错误归因。
- 自动评分明细报告：每个测试用例的通过 / 失败、得分与归因可展开核对，每分必有所据。

约束：

- 复用现有登录鉴权、作业存储模块：高校管理员与学生挂入现有角色框架，读写归属复查沿用现有模式；任务发布、提交与名单沿用班级作业框架，不新建账号体系，不另建作业系统；代码提交与判题记录按现有敏感字段要求加密留存。
- 沙箱单线程执行：判题沙箱串行处理提交，一次只运行一个判题任务；隔离、资源限额与单线程串行为上线前置条件，判题日志全程留痕。判题沙箱是独立于规则引擎的全新执行面，规则引擎不执行学生代码。
- 教学只使用仿真 / 教学数据，编程题与测试数据同样适用现有红线。

二期预留功能不进入上述业务主流程，仅作未来规划：师生批量导入（Excel 名单建号与账号班级批量绑定）、判题任务并发队列调度（排队、失败重试与状态机）、代码查重（班内与跨班同题比对）与代码质量规范评分（lint、编码规范、复杂度）。完整范围见 [产品需求文档](02-产品需求文档.md) 第十一节。
